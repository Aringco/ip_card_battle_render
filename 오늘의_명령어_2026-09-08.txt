4. 순위 아이콘을 5번으로 대체, 결과 페이지에서 각 팀 간 획득한 점수판(왼쪽 화면)에만

현재까지 구성된 내용들을 git render로 배포. (upstream의 Dockerfile, .dockerignore,

(→ Docker 파일 셋은 upstream과 **완전히 동일**해 손댈 것이 없었다(git diff가 비어 있다).
   진짜 문제는 다른 데 있었다.

   ⚠ **NEXT_PUBLIC_* 는 런타임 환경변수가 아니라 빌드 시점에 번들로 박히는 값이다.**
     그래서 기존 구조는 배포 도메인을 빌드 **전에** 알아야 했는데, Render는 서비스
     이름이 이미 쓰이고 있으면 도메인 뒤에 임의 문자열을 붙인다
     (ip-card-battle-render.onrender.com은 이미 upstream이 쓰고 있다).
     어긋나면 **화면은 멀쩡히 뜨는데 방만 안 만들어진다** — 찾기 가장 어려운 고장이다.

   그래서 클라이언트가 주소를 스스로 찾게 했다(useWebSocket.ts의 resolveWsUrl):
     ① NEXT_PUBLIC_WS_URL이 있으면 그것
     ② 없고 **개발 빌드**면 ws://localhost:8080
     ③ 없고 **프로덕션 빌드**면 이 페이지와 같은 호스트의 /ws
   **갈림길이 호스트가 아니라 빌드 모드인 것이 요령이다** — 로컬에서 Docker 이미지를
   띄우면 브라우저 주소가 개발 때와 같은 localhost:3000인데 WS는 8080이 아니라 같은
   포트의 /ws에 있어, 호스트 이름으로는 둘을 가를 수 없다.

   ⚠ 그 대신 **로컬 프로덕션 검증 빌드에 NEXT_PUBLIC_WS_URL=ws://localhost:8080이
     필요해졌다** — 검증 서버(3200)에는 WS가 없고 8080에 따로 뜬다.
     CLAUDE.md·HANDOVER.md·NEXT_SESSION.md의 검증 절차를 함께 고쳤다.

   render.yaml(Blueprint) 추가. .dockerignore에 client/.next-verify·lobby-shots 추가
   (**/.next는 정확히 .next만 잡아서 .next-verify는 안 걸린다).

   Docker가 없는 환경이라 이미지 대신 **Dockerfile이 실행하는 그 명령**을 그대로 돌려
   확인했다(NODE_ENV=production ts-node --transpile-only server.ts, 3300) —
   ws://localhost:3300/ws 연결, 방 생성, 대기실, 혼자 놀기 게임 화면까지 정상.

   ⚠ **서비스 생성은 못 했다.** Render API 키·CLI가 없고, GitHub App 설치는 계정 승인
     화면을 거쳐야 한다. 저장소에 웹훅이 0개인 것으로 아직 연결 전임을 확인했다.

5. 버튼에 있는 글씨(예> 컴퓨터와 대전 시작 등)의 그림자가 밝은 색으로 되어있는데,
   어두운 색으로 변경하고 위쪽으로 shadow를 줘서 버튼에 음각으로 들어가 있는 느낌을

(→ ⚠ **2번을 되돌리자 그 기능이 원래 생긴 이유가 그대로 돌아왔다.** 가로 2열은
     "세로로만 자라면 스테이지를 넘친다"는 이유로 만들어진 것이었다(51d6d24).

   스크롤바 — **"보이는 굵기"와 "잡히는 폭"을 따로 둔 것이 핵심이다.** 손잡이를 정말
   2px로 만들면 마우스로 잡을 수 없다. 스크롤바는 10px로 두고 손잡이에 **투명한 테두리
   4px**을 둘러 색칠 영역만 2px로 보이게 했다(background-clip: padding-box).
   hover하면 테두리가 2px로 줄어 6px(radius 2px)이 되는데 잡히는 폭은 10px 그대로다.
   양끝 화살표(scrollbar-button)는 크기 0 — 안 두면 얇은 막대 위아래에 회색 사각형이 남는다.
   Firefox는 scrollbar-width/color까지만 받는다.

   ⚠ **헤드리스 Chrome이 webkit 스크롤바를 그리지 않아 사진으로 확인하지 못했다.**
     빌드된 CSS에 6개 규칙이 들어간 것과 scrollbar-color가 실제 요소에 적용된 것까지
     확인했다. 실제 브라우저에서 한 번 봐야 한다.

   음각 — hover의 transform도 걷어냈다. 판이 떠오르면 글씨도 함께 움직여 파인 느낌이 깨진다)

참고 — 이 날 배운 것
══════════════════════════════════════════════
· **첨부 이미지는 JPEG로 도착한다 — 투명한 자리가 무엇으로 칠해졌는지 먼저 볼 것.**
  같은 "배경 제거"인데 세 번 다 기준이 달랐다.
      아이콘 시트   검은 배경     → 테두리에서 이어진 near-black(≤20) flood fill
      가로 팻말     어두운 글로우 → "밝기 130 이상 = 나무판"으로 뒤집어 판단
      빈 나무판     흰 배경       → 테두리에서 이어진 near-white(≥232) flood fill
  **먼저 모서리와 중앙선의 실제 화소값을 찍어보고 문턱을 정한다.** 지난 기준을 그대로
  가져다 쓰면 아무것도 안 지워지거나 그림이 뚫린다.

· **"가장 큰 밝은 연결 성분"으로 대상을 고르지 말 것.** 팻말이 짙은 나뭇결로 쪼개져
  안쪽 그림 띠가 더 크게 잡히면서 나무테와 글씨가 통째로 잘려 나갔다.
  **배경 쪽에서 flood fill로 접근하면** 대상이 몇 조각이든, 안쪽이 아무리 짙든 살아남는다.

· **잘라낸 결과는 반드시 두 가지 배경 위에 합성해 눈으로 볼 것.** 양피지색과 초록 펠트.
  2026-09-05에 이 확인을 빼먹어 검은 타원이 그대로 배포된 적이 있다.

· **되돌리기 전에 "그게 왜 생겼는지"를 먼저 찾을 것.** 가로 2열을 되돌리자 그것이
  해결하던 넘침이 그대로 돌아왔다. git log -S 로 도입 커밋을 찾으면 커밋 메시지에 이유가
  적혀 있다. 되돌림은 공짜가 아니라 **그 이유를 다시 감당하겠다는 결정**이다.

· **측정 도구가 늑대소년이 되게 두지 말 것.** 규칙 펼침 스크롤이 의도된 동작이 된
  순간부터 measureLobby가 매번 12건을 뱉었다. 도구를 함께 고쳐 "무엇이 진짜 문제인지"의
  기준을 옮겨 적어야 다음 사람이 그 표를 믿는다.

· **UI 배수를 요청받으면 지금 화면에 무엇이 그려지고 있는지부터 확인할 것.**
  "0.2배로 축소"가 256px 기준이라 말이 됐던 것은, 그때 dev 서버가 낡은 CSS를 내주어
  아이콘이 원본 크기로 그려지고 있었기 때문이다. 클래스 이름(w-10 = 40px)이 아니라
  **실제로 그려지던 크기**(32px)를 기준으로 삼아야 한다.

· **NEXT_PUBLIC_* 는 빌드 시점에 번들로 박힌다.** 배포 도메인을 빌드 전에 알아야 하는
  구조를 만들지 말 것 — 한 글자만 어긋나도 화면은 뜨고 방만 안 만들어진다.
  같은 호스트에 얹히는 구조라면 클라이언트가 window.location으로 찾게 하는 편이 안전하다.

· **긴 텍스트 파일은 heredoc 대신 파일 쓰기 도구로 만들 것.** 이 파일을 처음에
  `cat <<'EOF'`로 쓰려다 셸 파싱 오류로 실패했다(따옴표·역따옴표가 섞인 긴 본문).
