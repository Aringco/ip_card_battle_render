── 이 날의 큰 줄기 ────────────────────────────────────
하루 종일 **로비 버튼의 겉모습**을 다듬었고, 중간에 **배포 구성**이 끼어들었습니다.
버튼은 세 번 형태가 바뀌었는데, 뒤로 갈수록 "그림에 글씨를 넣지 않는" 쪽으로 갔습니다.

  ① 아이콘만 있는 그림   → 글씨는 HTML로       (아이콘 5종)
  ② 글씨까지 그려진 팻말 → 라벨을 안 씀        (가로 팻말 2종)  ← 뒤에 폐기
  ③ **빈 나무판 + HTML 글씨**                  (btn_plank)      ← 최종

③이 이긴 이유가 이 날의 교훈입니다 — 문구가 상태에 따라 바뀌는 버튼("준비" ↔
"준비 완료 ✓", "규칙 적용" ↔ "적용됨 ✓")은 글씨가 박힌 그림으로는 만들 수 없습니다.

나무판 그림 자체도 하루에 세 번 갈아끼웠습니다.

밤에는 **게임 방법 창**([7][8])과 **영문 글꼴**([9])이 이어졌고, 그 사이에서
**"게임 규칙 펼치기"의 동작이 이 날에만 네 번 바뀌었습니다.** 마지막 [9]는 자정을
막 넘겨 끝났지만, 요청은 모두 이 날 것이라 한 파일에 담았습니다.

  ① 카드가 세로로 자람 + 폼 전체 스크롤   ← 액자까지 밀려 올라가 폐기        [6]
  ② 카드 안쪽만 스크롤 (max-height)                                          [7]
  ③ 높이를 아예 못박음 (height)           ← 접었을 때 여백이 휑해 지적받음   [8]
  ④ **max-height + 펼칠 때 scrollIntoView**                    ← 최종        [9]

되돌아온 셈이지만 ②와 ④는 다릅니다 — ④에는 "펼쳤는데 규칙이 화면 밖에 있는" 경우를

[1] 아이콘 시트를 배경 제거판으로 교체 — 이미지 1장 첨부

4. 순위 아이콘을 5번으로 대체, 결과 페이지에서 각 팀 간 획득한 점수판(왼쪽 화면)에만

5. 방만들기 아이콘을 2번으로 대체, 방 만들기라고 함은 멀티 플레이에서 방을 생성할 때

현재까지 구성된 내용들을 git render로 배포. (upstream의 Dockerfile, .dockerignore,

   ⚠ **NEXT_PUBLIC_* 는 런타임 환경변수가 아니라 빌드 시점에 번들로 박히는 값이다.**
     그래서 기존 구조는 배포 도메인을 빌드 **전에** 알아야 했는데, Render는 서비스

     ① NEXT_PUBLIC_WS_URL이 있으면 그것
     ② 없고 **개발 빌드**면 ws://localhost:8080
     ③ 없고 **프로덕션 빌드**면 이 페이지와 같은 호스트의 /ws
   **갈림길이 호스트가 아니라 빌드 모드인 것이 요령이다** — 로컬에서 Docker 이미지를
   띄우면 브라우저 주소가 개발 때와 같은 localhost:3000인데 WS는 8080이 아니라 같은
   포트의 /ws에 있어, 호스트 이름으로는 둘을 가를 수 없다.

   ⚠ 그 대신 **로컬 프로덕션 검증 빌드에 NEXT_PUBLIC_WS_URL=ws://localhost:8080이
     필요해졌다** — 검증 서버(3200)에는 WS가 없고 8080에 따로 뜬다.
     CLAUDE.md·HANDOVER.md·NEXT_SESSION.md의 검증 절차를 함께 고쳤다.

   render.yaml(Blueprint) 추가. .dockerignore에 client/.next-verify·lobby-shots 추가
   (**/.next는 정확히 .next만 잡아서 .next-verify는 안 걸린다).

   Docker가 없는 환경이라 이미지 대신 **Dockerfile이 실행하는 그 명령**을 그대로 돌려

   ⚠ **서비스 생성은 못 했다.** Render API 키·CLI가 없고, GitHub App 설치는 계정 승인

══════════════════════════════════════════════

(→ 1번 — font-family를 var(--font-comic), var(--font-cafe24), … 순으로 둔다.
   **한글 글꼴과 나란히 쓰는 것이 아니라 목록에서 앞에 두는 것이 전부다.**
   Comic Relief에는 한글 글리프가 없으므로 브라우저가 글자마다 목록을 훑어
   영문·숫자·문장부호는 앞에서, 한글은 뒤에서 가져온다. unicode-range로 라틴만 잘라도
   되지만 순서만으로 같은 결과가 나오고 어떤 문자가 어느 글꼴에 있는지 손으로
   관리하지 않아도 된다. ⚠ **둘의 앞뒤를 바꾸면 영문까지 Cafe24로 그려진다.**
   받은 것이 ttf뿐이라 그대로 쓴다 — 라틴 전용이라 79KB/93KB로 가볍고(한글 글꼴은
   같은 이유로 woff2가 꼭 필요했다), Regular·Bold가 둘 다 있어 합성 볼드를 안 쓴다.

   부딪힌다:** ① 접었을 때 판은 내용만큼만 ② 펼쳐도 판이 커지면 안 됨.

       카드가 자라고 폼 전체가 스크롤   → 나무 액자까지 밀려 올라감          ([6]에서 폐기)

       펼침 몸통을 position: absolute   → 몸통이 보이는 영역 밖으로 나감      (이번에 폐기)
       **max-height + scrollIntoView**  → **채택**

   세 번째는 이론상 완벽했다 — 판이 1px도 안 움직이고(절대배치는 부모 높이에 안
   보태진다) 스크롤도 걸린다(절대배치 자손도 스크롤 높이에는 잡힌다). **그런데 몸통이
   통째로 보이는 영역 밖에 놓여 "펼치기를 눌러도 아무 일도 없는" 화면이 됐다.**
   만들어 화면을 보고서야 알았다.

   ⚠ 채택한 방식에는 **펼칠 때 scrollIntoView({ block: 'nearest' })가 반드시 필요하다.**
     접힌 내용이 이미 상한에 가까우면 펼쳐도 규칙이 보이는 영역 밖에 놓인다 —
     1440×950에서 카드가 528 → 537px(상한)까지밖에 못 자라 실제로 그렇게 됐다.

   검증 — 접힘은 내용 크기(528/380), 펼치면 상한까지 자란 뒤 규칙 일곱 줄이 모두
   보이는 것을 1440·390에서 확인. "HOW TO PLAY"를 확대해 Comic Relief로 그려지고
   한글은 Cafe24로 남는 것도 눈으로 확인했다.)

참고 — 이 날 배운 것
══════════════════════════════════════════════
· **첨부 이미지는 JPEG로 도착한다 — 투명한 자리가 무엇으로 칠해졌는지 먼저 볼 것.**
  같은 "배경 제거"인데 세 번 다 기준이 달랐다.
      아이콘 시트   검은 배경     → 테두리에서 이어진 near-black(≤20) flood fill
      가로 팻말     어두운 글로우 → "밝기 130 이상 = 나무판"으로 뒤집어 판단
      빈 나무판     흰 배경       → 테두리에서 이어진 near-white(≥232) flood fill
  **먼저 모서리와 중앙선의 실제 화소값을 찍어보고 문턱을 정한다.** 지난 기준을 그대로
  가져다 쓰면 아무것도 안 지워지거나 그림이 뚫린다.

· **"가장 큰 밝은 연결 성분"으로 대상을 고르지 말 것.** 팻말이 짙은 나뭇결로 쪼개져
  안쪽 그림 띠가 더 크게 잡히면서 나무테와 글씨가 통째로 잘려 나갔다.
  **배경 쪽에서 flood fill로 접근하면** 대상이 몇 조각이든, 안쪽이 아무리 짙든 살아남는다.

· **잘라낸 결과는 반드시 두 가지 배경 위에 합성해 눈으로 볼 것.** 양피지색과 초록 펠트.
  2026-09-05에 이 확인을 빼먹어 검은 타원이 그대로 배포된 적이 있다.

· **되돌리기 전에 "그게 왜 생겼는지"를 먼저 찾을 것.** 가로 2열을 되돌리자 그것이
  해결하던 넘침이 그대로 돌아왔다. git log -S 로 도입 커밋을 찾으면 커밋 메시지에 이유가
  적혀 있다. 되돌림은 공짜가 아니라 **그 이유를 다시 감당하겠다는 결정**이다.

· **측정 도구가 늑대소년이 되게 두지 말 것.** 규칙 펼침 스크롤이 의도된 동작이 된
  순간부터 measureLobby가 매번 12건을 뱉었다. 도구를 함께 고쳐 "무엇이 진짜 문제인지"의
  기준을 옮겨 적어야 다음 사람이 그 표를 믿는다.

· **UI 배수를 요청받으면 지금 화면에 무엇이 그려지고 있는지부터 확인할 것.**
  "0.2배로 축소"가 256px 기준이라 말이 됐던 것은, 그때 dev 서버가 낡은 CSS를 내주어
  아이콘이 원본 크기로 그려지고 있었기 때문이다. 클래스 이름(w-10 = 40px)이 아니라
  **실제로 그려지던 크기**(32px)를 기준으로 삼아야 한다.

· **NEXT_PUBLIC_* 는 빌드 시점에 번들로 박힌다.** 배포 도메인을 빌드 전에 알아야 하는
  구조를 만들지 말 것 — 한 글자만 어긋나도 화면은 뜨고 방만 안 만들어진다.
  같은 호스트에 얹히는 구조라면 클라이언트가 window.location으로 찾게 하는 편이 안전하다.

· **긴 텍스트 파일은 heredoc 대신 파일 쓰기 도구로 만들 것.** 이 파일을 처음에
  `cat <<'EOF'`로 쓰려다 셸 파싱 오류로 실패했다(따옴표·역따옴표가 섞인 긴 본문).

· **실측이 "문제 0건"이라고 화면이 멀쩡한 것은 아니다.** 이 날만 두 번 겪었다 —
  카드가 1.35배 작게 떠 있던 것도, 팻말이 첫 줄을 덮고 있던 것도 실측은 통과시켰다.
  **재는 것과 보는 것은 다른 일이다.** 크기를 바꿨으면 스크린샷을 한 장 찍어 볼 것.

· **반대로, 눈으로 못 찾는 것은 상자를 직접 찍어봐야 한다.** 액자가 카드 상자 밖으로
  더 그려져 폼이 넘친 건은 화면상 아무 단서가 없었다. 세 상자의
  client·offset·rect·zoom을 나란히 찍어보고서야 오버행이 범인이라는 게 드러났다.
  **`::before`로 그린 액자는 요소 크기에 포함되지 않는다** — 100%를 주면 그만큼 넘친다.

· **요즘 브라우저의 `zoom`은 퍼센트를 이미 보정해서 해석한다.** 확대분으로 한 번 더
  나누면 그만큼 작아진다. 옛 지식을 그대로 적용하기 전에 실제 값을 재볼 것.

· **잘라낸 조각을 각자 경계상자로 바짝 자르지 말 것.** 네 귀퉁이처럼 함께 놓일
  조각이라면 **원본에서의 상대 위치가 곧 정렬 정보**다. 공유 캔버스에 모서리 기준
  오프셋을 남겨 두면 CSS 한 줄로 넷이 함께 움직인다.

· **"고정"과 "내용만큼"은 같은 축에서 동시에 만족할 수 없다.** 규칙 펼침이 이 날에만
  네 번 바뀐 이유다. CSS로 안 되는 요구를 CSS로 계속 밀지 말고, 어느 쪽을 포기할지
  먼저 정한 뒤(여기서는 "펼치면 상한까지는 자란다") 나머지를 스크립트로 보완할 것.

· **되돌린 자리에는 무엇이 달라졌는지 남길 것.** ②로 되돌아온 것처럼 보이지만
  scrollIntoView가 붙어 있다. 이걸 안 적어두면 다음 사람이 "왜 이게 붙어 있지" 하며
  떼어내고, 그 순간 "펼쳤는데 아무 일도 없는" 화면이 그대로 돌아온다.
