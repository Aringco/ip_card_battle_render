# AI 로드맵 — 컴퓨터 지능 · 카드 추천 · 재미있는 규칙 추천

> 2026-11-24 작성. **아직 아무것도 만들지 않았다** — 실행 전에 거쳐야 할 순서와 정할 것을 적어 둔 문서다.
> 세 기능은 모두 **"엔진으로 앞날을 굴려 보는 판단 함수" 하나** 위에 선다. 그 함수가 먼저다.

## 0. 방향 요약

| 기능 | 판단을 맡는 것 | 언어 모델(LLM)의 자리 |
| --- | --- | --- |
| 컴퓨터 상대 지능 | 탐색 봇(몬테카를로) → 필요하면 가치망(작은 신경망) | 없음 |
| 다음 카드 추천 | 같은 탐색 함수의 1위 + 근거 숫자(승률) | (선택) 이유를 한 줄 문장으로 |
| 재미있는 규칙 추천 | 시뮬레이션 재미 지표 + 규칙 최적화 → 실사용 기록 + 밴딧 | (선택) 프리셋 이름 · 설명, 기획 보조 |

**LLM에게 판단을 맡기지 않는다** — 배율 · 쿨타임 · 출혈 · 보호막이 얽힌 수치 계산을 추측으로 틀리고,
이미 있는 엔진(`server/engine/`, 순수 함수 · RNG 주입 가능)이 규칙과 100% 같은 답을 더 빨리 준다.

### 서버 사양 (2026-11-24 실측)

| 항목 | 상태 | 영향 |
| --- | --- | --- |
| CPU | Xeon E5-2667 v2 16스레드, **AVX2 없음** | 탐색 · 작은 모델 추론은 충분, CPU로 LLM은 매우 느림 |
| GPU | RTX 3060, **NVIDIA 드라이버 미설치**(nouveau) | 학습 · LLM에 쓰려면 드라이버 설치 + 재부팅(운영 컨테이너도 멈춤) |
| 메모리 | 31GB(사용 1.5GB) | 여유 |
| 디스크 | **15GB 남음**(85%) | LLM 하나 5~8GB — 먼저 비워야 함 |

## 1단계 — 준비 (코드 기반 다지기)

탐색 봇을 만들기 전에 엔진이 "수백 번 복사해 굴리기"를 견디는지 확인한다.

- [ ] **상태 복사**: 엔진 진입점(`processPlayerAction` · `processSkillChoice` · `processPass` · `processAcornPick`)이
      상태를 직접 고치는지 확인하고, 탐색용 복사(`structuredClone`) 비용을 잰다. 큰 판(강화 판 후반)에서 특히.
- [ ] **무작위 주입 정리**: 엔진은 `rng`를 받지만 컴퓨터 쪽은 `Math.random`을 직접 쓴다
      (`server/computerSkills.ts`, `room.ts`의 컴퓨터 장소 · 도토리 고르기). 재현 가능한 실험을 위해 rng를 받게 바꾼다.
- [ ] **봇 인터페이스 하나로**: 지금 컴퓨터의 판단은 세 곳에 흩어져 있다 — 장소(`room.ts`, 무작위) ·
      기술(`pickComputerSkill` / `pickEnhanceComputerSkill`) · 도토리(`room.ts`, 무작위).
      `decide(state, side, rng) → 행동` 하나로 묶어 기존 봇을 그 첫 구현으로 둔다(동작은 그대로).
- [ ] **대전 시험장**: 봇 A vs 봇 B를 N판 붙여 승률 · 판 길이 · 한 수 판단 시간을 내는 스크립트
      (`server/scripts/`의 `enhanceStrategySim.ts`를 바탕으로). 이후 모든 단계의 성적표다.
- [ ] **기준선 기록**: 현재 봇끼리의 성적(일반 팀전 · 강화 1:1 · 개인전)을 남겨 둔다.

**끝난 기준**: 기존 봇이 새 인터페이스로 돌고, 시험장이 같은 시드에서 같은 결과를 낸다. 일반 게임 테스트가 그대로 통과한다.

## 2단계 — 탐색 봇 (컴퓨터 지능)

- [ ] **몬테카를로 탐색**: 지금 고를 수 있는 행동마다 상태를 복사해 그 행동을 두고, 이후를 빠른 봇(기존 봇)으로
      끝까지 또는 K턴까지 굴려 결과(승패 · 체력 차)를 평균낸다. 가장 좋은 행동을 고른다.
- [ ] **판단 시간 예산**: 한 수 300ms 안(추정 목표 — 1단계 실측으로 다시 정한다). 강화 판의 큰 예약 뽑기는 굴리는 비용이 크므로
      굴림 깊이를 턴 수로 자른다.
- [ ] **난이도**: 굴림 횟수로 쉬움 · 보통 · 어려움을 나눈다. 쉬움은 지금 봇에 가깝게(사람처럼 실수).
- [ ] **연출 유예 지키기**: 판단이 길어도 `settleGraceMs` 뒤에 둔다는 규칙(CLAUDE.md "행동 선택은 반드시…")은 그대로.
      서버 이벤트 루프를 막지 않는지 확인(필요하면 worker thread).
- [ ] **검증**: 시험장에서 탐색 봇 vs 기존 봇 승률이 뚜렷이 높아야 한다(목표 70%+, 정할 것).

**정할 것**: 어느 판부터 적용할지(혼자 놀기 일반 · 강화 · 개인전 봇), 기본 난이도.

## 3단계 — 다음 카드 추천

2단계 함수를 그대로 쓰고 화면에 띄우기만 한다.

- [ ] **서버에서 계산해 보낸다**(서버가 진실 구조 유지) — 내 행동 선택 단계가 열릴 때 그 사람에게만 `hint` 메시지.
- [ ] **표시**: 기술 카드 위 표식 + 근거 숫자("승률 62% · 다음 58%"). PC · 모바일(`SkillChoiceBar` · 모바일 카드 띠) 모두.
      ⚠️ 시연 모드 · 관전자 분기를 빠뜨리지 말 것.
- [ ] **켜고 끄기**: 방 규칙 또는 개인 설정.
- [ ] (선택) **이유 한 줄**: 처음에는 규칙 기반 문장("상대가 출혈 중 — 공격이 유리")으로. LLM은 그 뒤에 검토.

**정할 것(공정성)**: 혼자 놀기에만 켤지, 다같이 놀기 · 개인전에서도 방장이 허용할지.

## 4단계 — 재미 지표와 규칙 프리셋 (데이터 없이)

- [ ] **재미 지표 정의** — 판 길이(목표 범위 안) · 역전 횟수 · 마지막 체력 차(접전) · 선공 승률(50% 근처) ·
      "정답이 하나뿐인 차례" 비율 · 지루한 판(회복으로 굳어 오래 끄는 판) 비율. **가중치는 기획 판단 — 함께 정한다.**
- [ ] **규칙 탐색기**: `GameSettings` 범위(`clampSettings` · `clampEnhanceSettings`) 안에서 베이지안 최적화
      (Optuna — Python, 시뮬레이션은 Node 스크립트 호출) 또는 유전 알고리즘으로 점수가 높은 조합을 찾는다.
      ⚠️ 2단계 탐색 봇으로 돌려야 한다 — 약한 봇으로 찾으면 "봇에게 재미있는 규칙"이 나온다.
- [ ] **프리셋 3~4개**: 성격이 다른 조합("빠른 난타전" · "역전 많은 판" · "긴 전략전")을 로비에서 고르게.
      로비 폼에 넣으면 반드시 `measureLobby.mjs`로 다시 잰다.
- [ ] **사람 확인**: 프리셋마다 실제로 몇 판 해 보고 지표와 느낌이 맞는지 본다.

## 5단계 — 실사용 기록과 추천 (데이터 수집)

- [ ] **저장소 정하기**: 지금은 기록할 곳이 없다(이벤트 모드와 함께 Postgres 기록을 걷었다). 파일(JSONL) · SQLite · Postgres 중 선택.
- [ ] **기록 항목**: 판마다 규칙 · 인원 · 판 길이 · 승패 · 지표 · **다시 하기를 눌렀는지 · 중간에 나갔는지**(실제 재미 신호).
- [ ] **개인정보**: 사람별 추천을 하려면 식별 방법과 동의가 필요하다. 처음에는 방 · 인원 구성 단위(익명)로만.
- [ ] **밴딧 추천**: 톰슨 샘플링으로 프리셋을 고른다(잘 먹힌 쪽 위주 + 가끔 다른 것) — 모델 파일 없이 수십 줄.
- [ ] **보정**: 기록으로 4단계 재미 지표의 가중치를 고친다(시뮬레이션 지표와 실제 재미가 어긋날 수 있다).

## 6단계 — 학습 모델 (필요할 때만)

- [ ] **언제**: 탐색 봇이 판단 시간 예산을 넘기는 판이 실제로 생기거나, 탐색 봇으로도 부족할 때.
- [ ] **가치망**: 탐색 봇의 기록으로 "이 판이 몇 % 유리한가"를 배우는 작은 신경망(또는 LightGBM) → 탐색을 짧게 끊는다.
      서버 추론은 `onnxruntime-node`, 학습은 GPU(드라이버 설치 필요).
- [ ] **재학습 규칙**: 밸런스 표(`shared/enhance.ts` 등)가 바뀌면 다시 학습해야 한다 — CI에서 성능 회귀를 보는 장치가 필요하다.
- [ ] **기록이 수천 판 넘으면**: "이 구성에 이 규칙이면 다시 할 확률" 예측 모델로 5단계 추천을 개인화.

## 7단계 — 언어 모델 (선택)

- [ ] 전제: GPU 드라이버 설치 + 재부팅(운영 점검 시간), 디스크 확보.
- [ ] 실행: Ollama(Docker). 후보(4비트, 12GB): Qwen3 8B(Apache 2.0) · Gemma 3 12B(Gemma 약관) ·
      EXAONE 3.5 7.8B(비상업 라이선스 — 공개 서비스면 조건 확인). 작성 시점 기준이니 그때 다시 고른다.
- [ ] 쓰임: 추천 이유 문장 · 프리셋 이름과 설명 · 기획 보조(새 규칙 아이디어 → 4단계로 검증). **판단은 맡기지 않는다.**
- [ ] 실패해도 게임은 돌아야 한다 — 응답이 늦거나 없으면 규칙 기반 문장으로 대신한다.

## 순서와 의존 관계

```
1 준비 ─→ 2 탐색 봇 ─┬─→ 3 카드 추천
                     └─→ 4 규칙 프리셋 ─→ 5 기록 · 밴딧
                              6 학습 모델 (2 · 5가 한계에 닿으면)
                              7 언어 모델 (3 · 4의 문장 담당, 선택)
```

## 위험

- **시뮬레이션 재미 ≠ 사람 재미** — 4단계 결과는 5단계 실사용 기록으로 보정해야 한다.
- **규칙이 자주 바뀌는 단계** — 학습 모델은 표가 바뀔 때마다 다시 학습해야 해서, 학습이 필요 없는 탐색 봇을 먼저 둔다.
- **서버 부하** — 탐색이 이벤트 루프를 막으면 같은 서버의 모든 방이 느려진다. 2단계에서 판단 시간을 반드시 잰다.
- **공정성** — 다인전에서 추천을 켜면 실력 차가 줄어든다. 방 규칙으로 드러내 놓는다.
