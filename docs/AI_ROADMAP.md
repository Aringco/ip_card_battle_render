# AI 로드맵 — 컴퓨터 지능 · 카드 추천 · 재미있는 규칙 추천

> 2026-11-24 작성 · 같은 날 2판(실측 · 모델 조사 · 보완점 반영). **아직 아무것도 만들지 않았다** — 실행 전에 거칠 순서와 정할 것을 적은 문서다.
> 세 기능은 모두 **"엔진으로 앞날을 굴려 보는 판단 함수" 하나** 위에 선다. 그 함수가 먼저다.

## 0. 결론 먼저

| 기능 | 현실성 | 판단을 맡는 것 | 언어 모델(LLM)의 자리 |
| --- | --- | --- | --- |
| 컴퓨터 상대 지능 | **높음** — 지금 서버로 충분(§1 실측) | 몬테카를로 탐색 봇 | 없음 |
| 다음 카드 추천 | **높음** — 탐색 봇이 있으면 화면 작업뿐 | 같은 탐색 함수의 1위 + 승률 숫자 | 없어도 된다(이유 문장은 규칙 기반으로 충분) |
| 재미있는 규칙 프리셋 | **중간** — 계산은 되지만 "재미"의 정의를 사람이 정해야 한다 | 시뮬레이션 지표 + 규칙 탐색 | 개발 때 Claude Code로 이름 · 설명을 쓰면 끝(실행 중 호출 불필요) |
| 실사용 기록 · 개인화 추천 | **낮음(지금은)** — 이용자 수 · 저장소 · 동의가 먼저 | 밴딧 → (수천 판 뒤) 예측 모델 | 없음 |
| 실행 중 LLM(해설 · 대화) | **선택** — 재미는 있지만 게임에 필수가 아니다 | — | 관전 해설 · 판 끝 한 줄 평 정도 |

**원칙 셋.**

1. **판단은 엔진이 한다.** LLM은 배율 · 쿨타임 · 출혈 · 보호막이 얽힌 수치를 추측으로 틀리고, 이미 있는 엔진(`server/engine/`, 순수 함수 · RNG 주입 가능)이
   규칙과 100% 같은 답을 수천 배 빨리 준다.
2. **글은 개발 때 쓴다.** 프리셋 이름 · 설명 · 추천 이유 문장의 틀은 개발 중에 Claude Code로 만들어 저장소에 넣는다 — 실행 중 호출이 없으면
   비용 · 지연 · 장애 · 개인정보 문제가 함께 사라진다. 실행 중 LLM은 그래도 남는 쓰임(§7)에만 둔다.
3. **학습 모델은 마지막.** 밸런스 표(`shared/enhance.ts` — 6차 표까지 왔다)가 바뀔 때마다 다시 학습해야 해서, 학습이 필요 없는 탐색 봇을 먼저 둔다.

## 1. 실측 — 탐색 봇이 한 수에 몇 판을 굴릴 수 있나

`server/scripts/aiBench.ts`(2026-11-24, 개발 PC i5-10500 한 스레드, 무작위 정책, 기본 규칙):

| 판 | 한 판 끝까지 | 평균 턴 | 판 중간 상태 크기 · 복사 | **300ms 안에 판 중간부터 끝까지 굴리기** |
| --- | --- | --- | --- | --- |
| 팀전 1:1(일반) | 0.10ms | 8.9 | 3KB · 37µs | 약 4,800회 |
| 강화 1:1 | 1.1ms | 17.9 | 10KB · 128µs | 약 450회 |
| 개인전 4명(일반) | 0.19ms | 11.6 | 4KB · 54µs | 약 1,800회 |
| 개인전 4명(강화) | 2.6ms | 20.8 | 20KB · 253µs | 약 130회 |

**읽는 법.**

- 한 결정의 후보는 적다 — 장소 3곳(직전 장소 제외) · 기술 최대 4장 + 턴 마치기 · 도토리 후보. 후보 5개면 강화 1:1에서 **후보당 약 90번** 굴린다 —
  승률 차이를 가려내기에 충분하다. 그래서 **나무 탐색(MCTS) 없이 "평평한" 몬테카를로부터** 시작해도 된다.
- 개인전 강화는 후보당 20~30번뿐이라 거칠다 — **끝까지 굴리지 말고 K턴까지만 굴린 뒤 점수 함수로 끊는다**(§3).
- 서버 CPU(Xeon E5-2667 v2, 2013년)는 한 스레드가 이 PC보다 느리다 — **서버에서 `aiBench.ts`를 한 번 돌려 예산을 다시 정한다**(1단계 첫 할 일).
- `structuredClone` 복사는 굴리기 한 번의 10% 남짓이라 병목이 아니다.

## 3. 2단계 — 탐색 봇 (컴퓨터 지능)

- [ ] **평평한 몬테카를로**: 지금 고를 수 있는 후보마다 상태를 복사해 그 행동을 두고, 이후를 빠른 봇(기존 탐욕 봇)으로 굴려
      결과를 평균낸다. 후보마다 같은 횟수 대신 **UCB로 유망한 후보에 더 많이**(같은 예산으로 정확도가 오른다).
- [ ] **끊는 깊이 + 점수 함수**: 강화 판 · 개인전은 끝까지 굴리지 않고 K턴(시작값 3~5)까지만 굴린 뒤 점수로 평가한다 —
      `체력 차 + 승리선까지 남은 거리 + 레벨 합 × α + 지속 효과(출혈 · 회복 남은 양)`. α 같은 가중치는 시험장 승률로 맞춘다.
- [ ] **결정 지점 모두**: 장소 · 기술(여러 장 차례는 한 장씩) · 특허랑이 대상(개인전) · 도토리 고르기 · 턴 마치기.
- [ ] **판단 시간 예산**: 한 수 300ms(§1 서버 실측으로 다시 정한다). **이벤트 루프를 막지 않게 worker thread**로 돌린다 —
      ⚠️ 배포 이미지(`Dockerfile.nginx`)는 WS 서버를 `ts-node --transpile-only`로 띄우므로 worker도 같은 방식으로 띄워야 `.ts`를 읽는다.
      worker 수는 1~2(운영과 CPU를 나눠 쓴다).
- [ ] **연출 유예 지키기**: 판단이 길어도 `settleGraceMs` 뒤에 둔다는 규칙(CLAUDE.md "행동 선택은 반드시…")은 그대로. 판단 시간은
      유예 안에 숨긴다 — 유예가 보통 수 초라 300ms 판단은 사람이 느끼지 못한다.
- [ ] **난이도**: 굴림 횟수와 "가끔 차선 고르기"로 쉬움 · 보통 · 어려움. 쉬움은 지금 봇에 가깝게.
- [ ] **검증**: 시험장에서 탐색 봇(보통) vs 기존 봇 **승률 65% 이상**(정할 것). 한 수 최대 시간이 예산 안인지.
- [ ] **그림자 운영**: 실제 혼자 놀기에서 기존 봇이 두되, 탐색 봇도 같은 상황에서 판단만 해 로그로 남긴다(두 봇이 얼마나 다르게 고르는지 · 시간).
      문제가 없으면 스위치를 넘긴다.

**정할 것**: 어느 판부터(권장: **혼자 놀기 강화 1:1** — 판이 길고 결정이 많아 차이가 가장 잘 보인다), 기본 난이도.

### 3-1. 구현 현황 (2026-11-24) · 켜는 법 · 성능 시험 절차

**된 것** — 평평한 몬테카를로 + UCB1(`server/ai/searchBot.ts`), 롤아웃 정책은 지금 컴퓨터, 12턴 앞에서 끊고 체력 차로 매김.
결정 지점은 장소 · 기술(한 장씩) · 턴 마치기 · 도토리 고르기. 혼자 놀기(팀전 1:1, 일반 · 강화)만 — 개인전에는 컴퓨터가 없다.
**아직** — 난이도(쉬움 · 어려움), 점수 함수 다듬기(레벨 · 지속 효과), 개인전 · 대상 고르기.

**대비책**(`server/ai/pool.ts` — 서버가 느리거나 바빠도 게임이 느려지지 않게):

| 대비 | 구현 |
| --- | --- |
| 메인 스레드를 막지 않음 | 계산은 worker thread에서만(`ai/worker.ts`). ts-node 아래에서도 돈다(배포 이미지와 같은 방식) |
| worker 수 상한 | 기본 `min(2, 코어 − 2)`, `AI_WORKERS`로 정한다 |
| 바쁘면 예산 줄이기 | 밀린 일 > worker 수면 그 비율만큼 생각 시간을 줄임(최소 `AI_MIN_BUDGET_MS` 60) |
| 더 밀리면 대신 두기 | worker당 대기 `AI_QUEUE_PER_WORKER`(4)를 넘으면 받지 않음 → 지금 컴퓨터가 둔다. 마감까지 답이 없어도 같다 |
| 연출 시간에 숨기기 | 컴퓨터가 어차피 기다리는 시간(연출 유예 + 생각하는 척 1~3초)이 시작될 때 묻고, 그 시간이 마감이다 — 체감 지연 0 |
| worker 장애 | 오류 · 멈춤(예산 + 2초)이면 갈아 끼우고 그 수는 지금 컴퓨터가 둔다 |
| 같은 기계의 운영 보호 | 테스트 컨테이너 `--cpus`(기본 2) |
| 시험 전에는 꺼져 있음 | `AI_BOT` 기본 `off` — main에 합쳐도 지금 컴퓨터 그대로. `shadow`는 계산만 하고 쓰지 않는다 |

환경변수: `AI_BOT`(off · shadow · on) · `AI_WORKERS` · `AI_BUDGET_MS`(300) · `AI_MIN_BUDGET_MS` · `AI_QUEUE_PER_WORKER` · `AI_DEPTH_TURNS`(12) ·
`AI_STATS_SEC`(n초마다 `[ai]` 통계 한 줄 — 요청 · 거절 · 대신 둔 수 · 평균 롤아웃 · 응답 시간 · 이벤트 루프 지연).
⚠️ `--cpus` 상한은 컨테이너 안에서 코어 수로 보이지 않는다 — 켤 때는 `AI_WORKERS`를 직접 적는다.

**성능 시험 절차**(개발 PC → 서버 순서. 개발 중인 8080 서버를 건드리지 않게 다른 포트로):

```bash
cd server
# ① 엔진 속도(한 코어)
npx ts-node --transpile-only scripts/aiBench.ts
# ② 강함 — 기준선 vs 탐색 봇, B(후공) 승률
AI_WORKERS=2 npx ts-node --transpile-only scripts/aiMatch.ts 200 300 both
# ③ 부하 — 서버를 띄우고(터미널 1) 혼자 놀기 방 N개를 동시에(터미널 2). 방 수를 늘려 가며 [ai] 줄의 거절 · 대신 둔 수가 생기는 지점을 찾는다
AI_BOT=on AI_STATS_SEC=10 AI_WORKERS=2 PORT=8091 npx ts-node --transpile-only index.ts
npx ts-node --transpile-only scripts/aiLoadTest.ts --url ws://localhost:8091 --rooms 30 --duration 120
```

판정: ③에서 사람 쪽 응답 p99가 100ms 아래(메인 스레드가 막히지 않음), `[ai]`의 "대신 둔 수(준비 안 됨 · 거절)"가 실제 예상 동시 접속에서 0에 가까움.
서버에서는 테스트 컨테이너 안에서(`docker exec -it card-battle-test sh` → `cd /app/server`) 같은 명령을 쓴다 — ③의 서버는 컨테이너의 8080이 아니라 다른 포트로 하나 더 띄운다.

### 3-2. 대기실에서 봇 추가 — 혼자서도 여러 봇과 (2026-11-24 검토 → 같은 날 개인전으로 구현)

**구현된 것(2026-11-24)** — 정한 것: ① 혼자 놀기가 곧바로 시작하지 않고 대기실을 연다 ② 개인전만 ③ 봇마다 난이도(쉬움 · 보통 · 어려움, 줄의 드롭다운)
④ 일시정지 무제한, [게임 계속하기] 말고는 풀리지 않는다.

- 흐름: 혼자 놀기(일반 · 강화) 폼 → `createSoloRoom { lobby: true }` → 개인전 방에 나(방장) + 봇 하나(보통)로 대기실 → [🤖 + 봇 추가] · 난이도 · ✕(빼기) →
  [게임 시작]. 봇이 하나면 개인전 1:1이라 팀전 화면(`lib/duel.ts`)으로 그려져 예전 혼자 놀기와 같아 보인다. 시연 이름 짝(일반 판)은 예전처럼 팀전 컴퓨터와 곧바로 시작한다.
- 서버: `Room.addSoloLobbyPlayer` · `addBot` · `setBotLevel` · 빼기는 `kickPlayer`(봇 memberId). 봇은 `Room.bots`(연결 목록 밖), 자리 id `bot:N`.
  봇의 차례 판정은 `botSideNow`/`isBotSide`(옛 혼자 놀기는 B 그대로). 다른 사람은 들어올 수 없다(`addPlayer` → `'solo_room'`).
- 판단: 쉬움 `pickEasySkill`(무작위 · 넷에 하나 넘김) · 보통 `pickIndividualSkill`(끝낼 수 있으면 끝내기 · 대상 `pickTarget` = 끝낼 수 있는 사람 아니면 1위) ·
  어려움 = 탐색 봇(개인전으로 넓혔다 — 대상까지 후보, 순위 · 1위와의 체력 차로 매김), 답이 없으면 보통.
- 일시정지: 봇 방은 `vsComputer`라 횟수 · 시간 제한이 없다. **끊겨도 풀지 않는다**(`handleDisconnect` — 폰에서 다른 앱에 다녀오면 브라우저가 연결을 끊어
  판이 흐르던 원인. 옛 혼자 놀기도 같다). 멈춘 채 아무도 돌아오지 않으면 `SOLO_ABANDON_MS`(30분) 뒤 방을 정리한다.
- 시험: `__tests__/soloBots.test.ts`(대기실 · 봇 · 판 끝까지 · 일시정지 무제한 · 끊겨도 유지 · 정리) · `searchBot.test.ts`(개인전 대상) ·
  `scripts/aiLevels.ts`(난이도 대전) · `aiLoadTest.ts --bots N --level hard`(봇 방 부하).
- **남은 것**: 팀전 봇(사람 + 봇 섞인 팀) · 어려움이 너무 센지(아래 기록 — 1:1에서 보통을 92% 이긴다) · 대기실 폰 배치 측정(`measureLobby.mjs`는 아직 안 돌렸다).

아래는 구현 전 검토 원문이다.

**요청**: 지금 혼자 놀기는 대기실 없이 곧바로 컴퓨터 하나(B팀)와 시작한다. 대기실에 [봇 추가] 버튼을 두어 혼자서도 여러 봇을 상대하게 한다.

**결론 — 가능하다.** 엔진은 이미 "한 팀 여러 명"(팀 안에서 `activePlayerIndex`로 돌아가며 둔다 — 사람 여럿 팀전이 지금도 돈다)과
"개인전 최대 8편"을 안다. 대기실 · 방장 명령 · 시작 조건도 다같이 놀기 방에 이미 있다. 막는 것은 **지금 컴퓨터가 땜질로 붙어 있다는 점** 하나다.

| 지금 컴퓨터의 가정 (`server/room.ts`) | 봇 여럿이면 |
| --- | --- |
| 고정 id `'CPU'` 하나를 `teamPlayerIds.B`에 넣는다. `players`(연결 목록)에는 없고 닉네임은 `CPU_NICKNAME`으로 메운다 | 봇마다 id · `memberId` · 닉네임(· 개인전 색)이 필요하다 |
| 컴퓨터의 차례 판정 · 수 두기가 모두 `'B'`로 못박혀 있다(`scheduleComputerActionIfNeeded` · `performComputerAction`) | "지금 둘 사람(`expectedPlayerId`)이 봇인가"로 바꾼다. 팀 안에 사람과 봇이 섞여도 된다 |
| 컴퓨터 타이머가 하나(`computerTimer`) | 둘 사람은 언제나 하나라 그대로 쓴다. 예외는 도토리 카드 고르기(모두 동시) — 아직 안 고른 봇을 하나씩 차례로 |
| `vsComputer`면 일시정지 무제한 · 혼자 놀기 화면(모바일 배치 등) | 봇 방의 일시정지 규칙을 정해야 한다(아래 "정할 것") |
| 개인전 컴퓨터가 없다 — `pickComputerSkill`은 팀전 전용(상대를 뒤집어 구한다), 탐색 봇도 팀전 1:1만 | 개인전 봇은 새 판단이 필요하다: 특허랑이 대상 고르기(1위 노리기 · 체력 낮은 사람 끝내기), 순위 판정. ⚠️ `noTeamFlip.test.ts` 규칙을 지킬 것 |

**설계** — 봇을 연결 목록(`players`)에 섞지 않는다. 연결 목록을 도는 코드(브로드캐스트 · 재접속 · 끊김 · 준비 · 방장 승계 · 일시정지 투표
`askableIndividuals` · 빈 방 정리 `onEmpty`)가 많아, 연결 없는 항목이 섞이면 그 모든 자리를 고쳐야 한다. 대신 `Room.bots`(id → 닉네임 · 자리 · 색 ·
난이도)를 따로 두고, 자리 목록(`teamPlayerIds`)과 대기실 목록(`LobbyPlayer`에 `bot: true`)에만 싣는다. 그러면 봇은 늘 준비 완료, 일시정지 투표에서 빠짐,
사람이 모두 나가면 방이 정리됨이 저절로 맞는다.

**할 일** — 다섯 가지다.

1. **서버 — 대기실의 봇**: `addBot { seat, level? }` · `removeBot { memberId }`(방장만 · 시작 전만 — `requireHost`). 시작 조건(`startBlockReason`)은
   봇을 인원에 센다. 개인전 8자리 · 색(`firstFreeColor`) · 팀 이름 겹침 규칙은 그대로. 대기실 안내줄("봇 1을 넣었어요").
   방 시험은 `spectator.test.ts`처럼 가짜 WebSocket으로(`jest.useFakeTimers()` 필수).
2. **서버 — 봇이 두기**: 컴퓨터 판단을 "편 · 봇 id"로 일반화. 팀전은 지금 판단(`heuristicDecision`)과 탐색 봇(`searchDecision` — 편 기준이라 2:2도 그대로),
   개인전은 새 판단(대상 고르기 포함). 연출 유예(`settleGraceMs`) 뒤에 두는 규칙 · 탐색 봇 worker 풀(§3-1)은 그대로 쓴다 — 한 방 안에서는 언제나 한 봇만 생각하므로 봇 수가 늘어도 부하는 같다.
3. **화면 — 대기실**: 방장에게 팀 칸 · 개인전 명단마다 [+ 봇] 버튼, 봇 줄은 🤖 표시와 [빼기](추방 버튼 자리). 난이도를 두면 그 줄에 쉬움 · 보통 · 어려움.
   대기실은 안전영역 밖이지만 폰 배치가 있으니 `measureLobby.mjs`로 다시 잰다.
4. **화면 — 게임**: 봇 이름에 🤖. 개인전 색 · 순위표 · 결과 화면은 사람과 같은 길이다(닉네임 · 색만 쓰므로).
5. **혼자 놀기 입구**(정할 것 1): 지금 곧바로 시작하는 혼자 놀기는 그대로 두고, 다같이 놀기 방을 혼자 만들어 봇을 채우는 길을 연다(권장).
   원하면 혼자 놀기에 [봇과 여럿이] 입구를 따로 두어 그 대기실로 곧장 보낸다.

**순서와 크기** — ①② 팀전(사람 + 봇 섞인 2:2 · 3:3 포함) → ③④ 화면 → 개인전 봇(새 판단) → 난이도. 팀전까지 서버 1~2일 · 화면 1일,
개인전 봇 판단 1~2일(추정). 탐색 봇을 개인전에 쓰려면 N편 평가(내 순위 · 1위와의 체력 차)와 대상 후보 확장이 더 필요하다 — 그때까지 개인전 봇은 규칙형으로 둔다.

**위험** — `'B'` 못박음을 놓치면 봇이 A팀에서 영영 안 두거나, 사람 차례에 봇이 둔다(방 시험으로 양쪽 자리를 모두 본다). 혼자 놀기 · 시연
(`vsComputer` · `demo`)은 이 길을 타지 않게 그대로 둔다 — 시연 대본은 CPU가 움직이지 않는다는 전제다.

## 4. 3단계 — 다음 카드 추천

2단계 함수를 그대로 쓰고 화면에 띄우기만 한다.

- [ ] **서버에서 계산해 보낸다**(서버가 진실 구조 유지) — 내 행동 선택 단계가 열릴 때 그 사람에게만 `hint` 메시지. 계산은 연출 유예 동안.
- [ ] **표시**: 기술 카드 위 표식 + 근거 숫자("이 카드 승률 62% · 턴 마치기 54%"). PC · 모바일 모두.
      ⚠️ 시연 모드(`gameState.demo`) · 관전자(`myTeam === null` · 개인전 `mySide === null`) 분기를 빠뜨리지 말 것.
- [ ] **이유 한 줄은 규칙 기반**: 상태에서 바로 읽히는 문장 틀("상대가 출혈 중 — 공격이 유리", "다음 차례 쿨타임이 풀린다")을 개발 때 써 둔다.
- [ ] **켜고 끄기**: 혼자 놀기는 개인 설정, 다같이 놀기 · 개인전은 방 규칙(방장이 허용해야). 기본은 혼자 놀기만 켬.

**정할 것(공정성)**: 다인전에서 허용할지 — 허용하면 실력 차가 줄어드므로 방 규칙으로 드러내 둔다.

## 5. 4단계 — 재미 지표와 규칙 프리셋 (데이터 없이)

- [ ] **재미 지표 정의** — 엔진 이벤트에서 바로 셀 수 있는 것만: 판 길이(목표 범위 안) · 역전 횟수(체력 우위가 뒤집힌 수) ·
      마지막 체력 차(접전) · 선공 승률(50% 근처) · "정답이 하나뿐인 차례" 비율(탐색 봇의 1 · 2위 승률 차가 큰 차례) ·
      지루한 판(회복으로 굳어 오래 끄는 판) 비율. **가중치는 기획 판단 — 함께 정한다.**
- [ ] **규칙 탐색기**: `GameSettings` 범위(`clampSettings` · `clampEnhanceSettings`) 안에서 조합을 찾는다. 처음에는 **격자 + 무작위 탐색을 Node 스크립트 하나로**
      (Python · Optuna를 들이지 않는다 — 시뮬레이션이 이미 Node다). 결과가 갈리면 그때 베이지안 최적화.
      ⚠️ 2단계 탐색 봇으로 돌려야 한다 — 약한 봇으로 찾으면 "봇에게 재미있는 규칙"이 나온다. ⚠️ **개발 PC에서 돌린다**(운영과 CPU를 나눠 쓰지 않게).
- [ ] **프리셋 3~4개**: 성격이 다른 조합("빠른 난타전" · "역전 많은 판" · "긴 전략전"). 이름 · 설명은 개발 때 Claude Code로 쓴다.
      로비 폼에 넣으면 반드시 `measureLobby.mjs`로 다시 잰다.
- [ ] **사람 확인**: 프리셋마다 실제로 몇 판 해 보고 지표와 느낌이 맞는지 본다.

## 6. 5단계 — 실사용 기록과 추천 (데이터 수집)

- [ ] **저장소 정하기**: 지금은 기록할 곳이 없다(이벤트 모드와 함께 Postgres 기록을 걷었다). 처음에는 **JSONL 파일**(컨테이너 밖 볼륨)로 충분하다.
- [ ] **기록 항목**: 판마다 규칙 · 인원 · 판 길이 · 승패 · 재미 지표 · **다시 하기를 눌렀는지 · 중간에 나갔는지**(실제 재미 신호) ·
      **그 판의 커밋**(`/version`) — 밸런스 표가 자주 바뀌므로 어느 표에서 나온 기록인지 갈라야 비교가 된다.
- [ ] **개인정보**: 사람별 추천을 하려면 식별 방법과 동의가 필요하다. 처음에는 방 · 인원 구성 단위(익명)로만.
- [ ] **밴딧 추천**: 톰슨 샘플링으로 프리셋을 고른다(잘 먹힌 쪽 위주 + 가끔 다른 것) — 모델 파일 없이 수십 줄.
      의미 있는 결과에는 프리셋마다 수백 판이 필요하다 — **이용자 수가 그만큼 될 때 시작한다.**
- [ ] **보정**: 기록으로 4단계 재미 지표의 가중치를 고친다(시뮬레이션 지표와 실제 재미가 어긋날 수 있다).

## 7. 6단계 — 학습 모델 (필요할 때만)

- [ ] **언제**: 탐색 봇이 판단 시간 예산을 넘기는 판이 실제로 생기거나(개인전 강화가 가장 먼저 닿는다), 탐색 봇으로도 부족할 때.
- [ ] **가치망**: 탐색 봇의 기록으로 "이 판이 몇 % 유리한가"를 배우는 작은 모델 → K턴 굴림 뒤의 점수 함수를 대신한다.
      **처음에는 작은 MLP(수천 개 가중치)를 TypeScript로 직접 추론**한다(가중치는 JSON) — 네이티브 의존성이 없어 AVX2 없는 서버에서도 확실히 돌고,
      이 크기면 한 번에 수 µs다. 커지면 그때 `onnxruntime-node`(AVX2 없이 도는지 먼저 확인).
- [ ] **학습 장소**: 이 크기는 개발 PC CPU로 충분하다. 서버 GPU는 필요 없다.
- [ ] **재학습 규칙**: 밸런스 표가 바뀌면 다시 학습 — CI에 "고정 시드 시험장 N판" 성능 회귀 검사를 넣는다(CI 제한 20분 안).

### 8-1. 쓰임 — 개발 때 vs 실행 중

### 8-3. 붙일 때의 규칙

- [ ] **실패해도 게임은 돈다** — 응답이 늦거나(예: 2초) 없으면 규칙 기반 문장으로 대신한다. 게임 흐름에서 기다리지 않는다(비동기).
- [ ] **판단은 맡기지 않는다** — 문장에 들어가는 숫자(피해 · 승률)는 엔진이 계산해 넘기고, 모델은 문장만 만든다.
- [ ] **비밀값은 서버 환경변수로만**(`ANTHROPIC_API_KEY` — `shared/`에 두면 번들에 박힌다). 호출 수 상한 · 방당 쿨다운을 둔다.
- [ ] **닉네임 등 개인정보를 보내지 않는다** — "p1 · p2"처럼 편 이름으로 보내고 화면에서 닉네임으로 바꾼다.

## 순서와 의존 관계

```text
1 준비(서버 실측 · 봇 인터페이스 · 시험장) ─→ 2 탐색 봇 ─┬─→ 2-2 대기실 봇 추가(§3-2 — 규칙형 봇으로도 먼저 시작할 수 있다)
                                                      ├─→ 3 카드 추천
                                                      └─→ 4 규칙 프리셋 ─→ 5 기록 · 밴딧(이용자가 늘면)
                                                               6 학습 모델 (2 · 5가 한계에 닿으면)
                                                               7 언어 모델 (선택 — 개발 때 쓰는 글은 지금도 가능)
```

**권장 첫 묶음**: 1단계 + 2단계를 **혼자 놀기 강화 1:1에만** — 효과가 가장 잘 보이고, 다인전 공정성 문제가 없고, 서버 부하가 작다.

## 위험

- **시뮬레이션 재미 ≠ 사람 재미** — 4단계 결과는 사람 확인과 5단계 기록으로 보정해야 한다.
- **규칙이 자주 바뀌는 단계** — 탐색 봇은 엔진을 그대로 쓰므로 표가 바뀌어도 따라간다. 점수 함수 가중치 · 학습 모델은 다시 맞춰야 한다.
- **서버 부하** — 탐색이 이벤트 루프를 막으면 같은 서버의 모든 방이 느려지고, 테스트 컨테이너의 실험은 운영까지 느리게 한다(같은 기계).
- **봇의 미래 엿보기** — 굴림에 판의 rng를 쓰면 실제로 나올 카드를 알고 두는 봇이 된다(1단계 "무작위 주입 정리").
- **공정성** — 다인전에서 추천을 켜면 실력 차가 줄어든다. 방 규칙으로 드러내 놓는다.
- **외부 LLM의 데이터 · 비용** — 보내는 내용(편 이름 · 숫자만), 호출 상한, 키 보관을 정해 두고 시작한다.

## 정할 것 (함께)

1. 탐색 봇을 처음 적용할 판 — 권장: 혼자 놀기 강화 1:1.
2. 탐색 봇 목표 승률(기존 봇 상대)과 기본 난이도.
3. 추천을 다인전에서 허용할지.
4. 재미 지표의 가중치.
5. 실행 중 LLM을 쓸지, 쓴다면 API(외부 전송)와 로컬(GPU 드라이버 · 재부팅) 중 어느 쪽인지.
6. 대기실 봇(§3-2): 혼자 놀기 입구를 어떻게 둘지(지금 혼자 놀기는 그대로 + 다같이 놀기 방에 봇 — 권장) · 팀전 · 개인전 중 어디까지 ·
   봇마다 난이도를 고를지 · 사람이 한 명뿐인 봇 방의 일시정지 규칙(혼자 놀기처럼 무제한 권장).
